Every Urtentic organization is on a plan. This page explains how a verification is paid for and how to handle the responses your integration gets when an organization runs out of allowance or wallet balance. Plans and prices are on the **Billing** page of the [dashboard](https://app.urtentic.com).

## How a verification is paid for

<Steps>
  <Step title="Plan allowance first">
    Each plan includes a number of verifications per billing period. While that allowance lasts, a new verification is covered by the plan.
  </Step>
  <Step title="Wallet after that">
    Once the allowance is used up, each new verification is paid from the organization's prepaid USD wallet. It costs the sum of the prices of its workflow's plan-covered checks (document verification, liveness, video agreement, proof of residency, location intelligence, email check). The amount is reserved when the verification starts and charged when it finishes.
  </Step>
  <Step title="Refused when neither can pay">
    If the allowance is used up and the wallet can't cover another verification, starting one fails with HTTP `402`. See [Handling HTTP 402](#handling-http-402).
  </Step>
</Steps>

A verification only counts towards the plan, or is charged to the wallet, when it finishes as `SUCCESS`, `REJECTED` or `NEEDS_REVIEW`. These cost nothing:

- Verifications that end `ABANDONED`.
- Verifications rejected only because of a failure on our side, where every serious step error is `internal-error` or `network-error`.

Wallet charges are rounded up to the next cent. Each check's current price is shown on its card in the workflow builder.

<Note>
New organizations start with a 14-day free trial that includes 50 verifications.
</Note>

## Checks charged per use

Phone verification, government database checks and watchlist screening pay a third party every time they run, so they are never covered by the plan. Each use is charged to the wallet, on every plan.

| Check | When it's charged | If the wallet can't pay |
|---|---|---|
| Phone check | Each confirmation SMS, when it's sent. At most 5 per verification. | No SMS is sent. The verification ends `NEEDS_REVIEW`. |
| Government check | Each lookup, once per verification. The price depends on the database (BVN, NIN, driver's licence or voter's card). | The lookup is skipped. The verification ends `NEEDS_REVIEW`. |
| Watchlist screening | Each screening, once per verification | The screening is skipped. The verification ends `NEEDS_REVIEW`. |

If the SMS provider, the government database or the screening provider fails, the charge is refunded automatically.

## The wallet

The wallet is a prepaid USD balance. The organization's owner or an admin funds it from **Billing** > **Wallet**, between 10 and 10,000 USD per top-up. The owner is emailed when the balance drops below 5 USD.

<Warning>
Wallet funds don't expire, but they can't be withdrawn or refunded.
</Warning>

## Handling HTTP 402

[Start verification](/api-reference/introduction) returns `402 Payment Required` when the organization can't start a verification. The `code` tells you why:

| `code` | Meaning | What the organization needs to do |
|---|---|---|
| `QUOTA_EXCEEDED` | The plan's allowance is used up and the wallet can't cover another verification | Fund the wallet or move to a bigger plan |
| `TRIAL_EXPIRED` | The free trial has ended | Choose a plan |
| `PAYMENT_REQUIRED` | A renewal payment failed and the 7-day grace period is over | Update the payment method |
| `SUBSCRIPTION_REQUIRED` | The subscription was cancelled | Choose a plan |

```json 402 response
{
  "code": "QUOTA_EXCEEDED",
  "message": "Your plan's quota of 500 verifications has been reached and your wallet balance can't cover another one. Upgrade your plan or fund your wallet to continue.",
  "tier": "STARTER",
  "included": 500,
  "used": 500,
  "upgradeUrl": "/billing/checkout"
}
```

`used` is only set for `QUOTA_EXCEEDED`. During the 7-day grace period after a failed renewal payment, verifications keep working.

<CodeGroup>
```javascript JavaScript
const response = await fetch("https://api.urtentic.com/api/v1/verifications", {
  method: "POST",
  headers: {
    "X-CLIENT-ID": process.env.URTENTIC_CLIENT_ID,
    Authorization: `Bearer ${process.env.URTENTIC_SECRET_KEY}`,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({ flowId: "40f85c69-b27a-46e8-9115-691401acb5df" }),
});

if (response.status === 402) {
  const { code, message } = await response.json();
  // Don't retry: ask the organization's owner to fund the wallet or change plan.
  throw new Error(`Urtentic billing blocked this verification (${code}): ${message}`);
}
if (!response.ok) {
  throw new Error(`Starting the verification failed with HTTP ${response.status}`);
}
const { verificationId } = await response.json();
```

## Phone codes when the wallet is empty

If you build your own phone-check screen instead of using the [direct link](/sdk/direct-link/getting-started), request the code with the verification it belongs to:

```bash
curl -X POST https://api.urtentic.com/api/v1/workflows/{workflowId}/otp \
  -H "X-CLIENT-ID: ${CLIENT_ID}" \
  -H "Authorization: Bearer ${API_KEY}" \
  -H "Content-Type: application/json" \
  -d '{"key": "+2348012345678", "channel": "PHONE", "verificationId": "85c94e71-6e3f-4a19-b15c-781d8a876542"}'
```

The response says whether a code was actually sent:

```json
{ "sent": false }
```

`sent: false` means the organization's wallet couldn't pay for the SMS, so nothing was sent. Don't ask the person for a code. Submit the phone number without an OTP and let the verification continue. It ends `NEEDS_REVIEW`.

| Status | `code` | Meaning |
|---|---|---|
| `400` | `VERIFICATION_ID_REQUIRED` | `verificationId` is missing |
| `400` | `VERIFICATION_NOT_IN_PROGRESS` | The verification has already finished |
| `404` | `VERIFICATION_NOT_FOUND` | No verification with that ID in this organization and workflow |
| `429` | `SMS_LIMIT_REACHED` | This verification has already had 5 codes sent |

## Spotting a skipped check in results

A check skipped because the wallet couldn't pay appears on the verification as a step error with `errorType` `insufficient-balance` and `severity` `MEDIUM`:

- On the `phone-owner-validation` step for a phone check.
- On the `government-check` step for a government check, and on the `watchlist` step for a watchlist screening. These steps have `status` `402` and no `data`.

```json
{
  "stepId": "government-check",
  "status": 402,
  "error": {
    "severity": "MEDIUM",
    "errorType": "insufficient-balance",
    "message": "The government check was skipped because the wallet balance couldn't cover it"
  }
}
```

Use this to tell a balance problem apart from a genuine verification failure, for example to alert your own team instead of rejecting the customer.
